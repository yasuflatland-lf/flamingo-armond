# Pagination

> Single source of truth for the Relay-style Connection design used by the cards-by-cardgroup query and the Apollo client patterns that consume it. Cross-referenced from `docs/backend.md` and `frontend/CLAUDE.md`.

## Why Relay Connection (not offset/limit)

Relay-style Connection pagination (cursor-based) is chosen because:

- **Stable across mutations.** Offset pagination shifts rows when items are inserted or deleted mid-list, causing skips or duplicates for the client. A cursor anchors to a specific row — and, on the connections whose ordering column is mutable, to the ordering-key value that row held when the page was served, so editing the row cannot move the bookmark. The precise guarantee that unmutated rows are neither duplicated nor skipped across an edit, plus the boundary row's direction-dependent behavior and the deleted-boundary cases, are enumerated in [`docs/pagination/cursor-encoding.md` § "What v2 guarantees, and what it does not"](../../docs/pagination/cursor-encoding.md#what-v2-guarantees-and-what-it-does-not).
- **Cursor opaqueness.** Clients treat `cursor: ID!` as an opaque handle and pass it back unchanged. The server may change encoding without breaking clients.
- **Server-side determinism.** The server controls page boundaries, order, and tie-breaking, so clients cannot craft parameters that bypass ordering invariants.

## Schema-side conventions

### Use Connection over flat list for paginated queries

Paginated lists use Relay-style Connection types, not bare `[T!]!`. New paginated queries declare `<Type>Connection { edges, pageInfo, totalCount }` + `<Type>Edge { cursor, node }` and accept `(first, after, last, before, orderBy, orderDirection)`. The flat `[T!]!` shape is reserved for fixed small collections where pagination is meaningless.

### Migration via `@deprecated`

When migrating an existing flat list to a Connection type, keep the old field with `@deprecated(reason: "Use <newField>")` until all clients have moved over. Removing the old field in the same change breaks any unmigrated consumer.

## Server-side design

- **Tuple `(orderField, id)` comparison.** Ties on the order field would skip or duplicate rows. The repository emits `field op ? OR (field = ? AND id op ?)` rather than the Postgres-only `(a, b) > (?, ?)` row-constructor — the expanded form is dialect-portable. When `orderBy` is already `ID`, only `ORDER BY id` is emitted; otherwise `, id <dir>` is appended so the ordering is always total.
- **`+1` fetch trick for `hasNextPage`.** The usecase asks the repository for `first+1` rows. If the repository returns more than `first`, set `hasNextPage = true` and trim the trailing row. No second query is needed.
- **Page-size cap asymmetry (`maxPageSize` vs `pageCap`).** `maxPageSize = 100` is the user-facing cap enforced by the usecase; `pageCap = maxPageSize + 1` (101) is the repository-level limit that lets the `+1` trick survive a request at the documented maximum. Changing one without the other silently caps a layer below spec.
- **Usecase-side page caps reuse the package-wide constants; clamp closures stay per-aggregate.** `maxPageSize` / `defaultPageSize` are declared once in the `usecase` package (`card.go`); a new aggregate's `resolve*PageSize` MUST reuse them rather than declaring its own `<aggregate>MaxPageSize = 100`. A duplicate constant is the same drift risk the repository-side `repository.PageCap` consolidation removed. The per-aggregate `resolve*PageSize` clamp *closures*, by contrast, stay separate: a speculative shared `ResolvePageSize` was deliberately removed (see [`scope-discipline.md` § "Post-flight grep: helpers introduced but never wired"](scope-discipline.md#post-flight-grep-helpers-introduced-but-never-wired)) because the per-file variants carry nuances that do not collapse cleanly. Constant: shared. Clamp function: per-aggregate.
- **`repository.PageCap` / `ClampPageSize` are the single source of truth for the repository-side cap.** Each per-aggregate repo (`card.go`, `cardgroup.go`, `user.go`) previously carried its own `pageCap = 101` constant. The duplication risked one site drifting from the documented `maxPageSize + 1` invariant. The shared `repository.PageCap` constant + `ClampPageSize(want int) int` helper enforce the invariant in one place; per-aggregate repos clamp via `ClampPageSize(want)` rather than hand-rolling the boundary check. The same file (`backend/internal/repository/pagination.go`) also exports `InvertDir(d SortOrder) SortOrder` and `ReverseSlice[T any](xs []T) []T` for the backward pagination direction-flip + reverse path.
- **Backward pagination via direction-flip + reverse.** Natural SQL "give me N rows before X" is awkward. The repository inverts the `ORDER BY` direction, applies `LIMIT N+1`, then reverses the returned slice in memory. The usecase mirrors the trim logic on the leading edge so the page boundary stays at the tail.
- **Trim direction expressed by function name, not bool flag.** The usecase layer's `TrimAndDetect[T any]` and `TrimAndDetectBackward[T any]` are two functions, not one function with a `backward bool` parameter. Forward pagination trims the trailing extra row; backward pagination trims the leading extra row (because the repository already inverted the SQL order and reversed in memory). Encoding the direction in the function name keeps call sites self-documenting; a bool flag would force readers to remember the direction-to-side mapping. Both functions are generic over `T` so card / cardgroup / user / role pagination share one implementation.
- **`totalCount` via separate `COUNT(*)`.** `totalCount` is a separate `COUNT(*)` query scoped by `cardgroup_id` — extra DB round-trips for SQL simplicity, acceptable for `<= 10k` cards per group; revisit with a windowed estimate or denormalised counter if the cap grows. Run `COUNT` **before** the `first == 0 && last == 0` short-circuit so callers asking only for `totalCount` still get a real value.
- **`totalCount` MUST apply the same filter as the page query.** When a connection accepts a `search`/filter argument, a count that omits the filter makes `totalCount` lie under an active filter ("3 of 500" when only 3 match) — a Relay-contract violation. The robust shape mirrors `card.go`'s `ListCardsByCardgroupConnection`: the repository's page method runs its `COUNT(*)` on the *same filtered base query* and returns it, and the usecase captures that returned total inside the `assemblePage` fetch closure — never a standalone, filter-unaware `Count*` call. A standalone FK-scoped count helper is correct ONLY for a connection with no filter argument; do not borrow the unfiltered-aggregate count pattern (e.g. `master_catalog`'s `CountAdmin`) for a searchable connection. Regression that motivated this rule: the master-card read API initially used a search-unaware `CountByMasterCardgroup` and discarded the page method's search-aware total; the fix captured the filtered total and deleted the standalone count (which then had zero callers).
- **Three layers of enums kept in sync.** `model.CardOrderBy` (gqlgen schema strings), `usecase.CardOrderBy` (typed enum, same string values), `repository.CardOrderBy` (snake_case column names). The resolver translates model → usecase; the usecase translates usecase → repository. Each layer stays free of dependencies on the others — duplication is intentional.
- **`cursorFieldValue` errors on missing column.** A silent zero-value fallback (`time.Time{}`) would generate a wrong-but-valid SQL predicate and quietly skip rows. The usecase hydrates the column required by the active `orderBy` before calling the repository; a missing column is a caller bug — surface it as `gqlerr.Internal`.
- **A connection whose ordering column is mutable MUST emit v2 cursors.** An id-only (`v1:`) cursor forces the serving code to re-read the row and take its *current* ordering value, so editing that row between two page fetches moves the bookmark: the next page repeats rows already returned, or swallows every row that was still ahead. The `v2:` envelope carries `{id, orderBy, direction, orderKey}`, where `orderKey` is the ordering column's value captured at serve time, so the bookmark is immune to the edit. Mechanically: the usecase output carries `Ordering` (the effective `orderBy`/direction) plus an `OrderKeys` map (node id → serialized value); the resolver's `orderedCursorEncoder` turns those into the cursor; and `resolve*Cursor` prefers the embedded value over a re-read, falling back to the re-read only for v1/legacy cursors. Two invariants ride along and must not be dropped when adding another aggregate: a cursor whose embedded ordering disagrees with the request is `BAD_USER_INPUT`, and the per-aggregate scope check (owner for cardgroups, published-status for the catalog, deck/cardgroup membership for master cards and cards) still runs on **every ordering that hydrates a column off the row** — v2 included, since a cursor that can hydrate itself must not thereby skip the gate. Skipping it there would let a foreign row's ordering value become the boundary, and would turn the endpoint into an existence oracle. Every connection whose ordering key can move is on v2: `myCardgroupsConnection` (default `updated_at`), the master catalog (default `sort_order`), master cards (default `position`, admin-mutable) and cards (immutable `ID` by default, but the opt-in `DUE` / `UPDATED_AT` orderings both move). `adminUsersConnection` stays on v1 because it orders by the immutable `created_at`. Details: [`docs/pagination/cursor-encoding.md`](../../docs/pagination/cursor-encoding.md).
- **`orderBy: ID` may skip the cursor scope check — a sanctioned exception, not drift.** The scope-check invariant above is keyed on *hydration*: it protects the case where a foreign row's ordering value would be read off that row and become the page boundary. Under `ID` ordering there is nothing to hydrate — the id in the cursor **is** the boundary — so an out-of-scope id degrades to a bare lexical `id > X` predicate evaluated inside a page query that is already scoped (`FindPageByCardgroup` / `FindPageByMasterCardgroup` by parent id, `FindPageByOwner` by owner, `FindPublishedPage` by catalog visibility). No out-of-scope row can be returned, and the resulting page depends only on the *string* X, never on whether X exists — so it is not an existence oracle either. **The cost is a contract asymmetry**: the same foreign or unknown cursor is `BAD_USER_INPUT: cursor not found` under a hydrating ordering (`POSITION`, `DUE`, `UPDATED_AT`) but silently accepted under `ID`. Migrating a connection to v2 does not change this: `ID` stays a legal ordering on the v2 connections, and it stays the one ordering with nothing to hydrate.
  Both answers are allowed and the codebase deliberately carries both: `card.go` and `master_card.go` take the shortcut (return before `FindByID`), while `cardgroup.go` and `master_catalog.go` decline it and pay one lookup per page for a uniform "every cursor names a row you may see" contract. Pick one when adding a connection and **say which in the `resolve*Cursor` docstring**, the way `master_card.go` does — an unexplained early return reads as a missing guard. The shortcut's safety argument rests entirely on the page query already being scoped; a connection whose scope lives anywhere else must run the lookup. A reviewer flagging the early return as a dropped scope check is reading the invariant one level too broadly: the guard belongs to hydration, not to every cursor.
- **Cursor encoding happens exactly once, at the resolver→model boundary.** The usecase connection *output* carries RAW entity ids in its start/end cursor fields (and each edge keys off the raw `node.id`); the resolver's connection mapper applies the connection's encoder exactly once — on the one v1 connection (`admin_user`) that is `encodeCursor(out.StartCur)` / `encodeCursor(out.EndCur)` for `PageInfo` plus `cursor.Encode(node.id)` per edge; on the v2 connections (`cardgroup`, `master_catalog`, `master_card`, `card`) it is `enc := orderedCursorEncoder(out.Ordering, out.OrderKeys)`, then `encodeBoundaryCursor(enc, out.StartCur)` / `encodeBoundaryCursor(enc, out.EndCur)` for `PageInfo` plus `enc(node.id)` per edge. Calling an encoder in the **usecase** double-encodes (the resolver encodes again), producing `"v1:" + base64("v1:" + base64(id))`; the edges still work but `PageInfo.startCursor`/`endCursor` become undecodable, so a client feeding them back as `after`/`before` gets cursor-not-found (`BAD_USER_INPUT`). Every connection usecase (`card`, `cardgroup`, `master_catalog`, `master_card`, `admin_user`) stores raw ids in its output — never call `cursor.Encode` / `cursor.EncodeV2` in the usecase layer. Regression that motivated this rule: the master-card usecase pre-encoded `StartCur`/`EndCur`, double-encoding only the `PageInfo` cursors (edge cursors were fine because they used the raw `node.id`), so the bug slipped past edge-cursor tests; the round-trip guard `cursor.Decode(pageInfo.startCursor) == node.id` at the resolver layer pins it closed.

## Frontend cache patterns

- **`cache.modify` skips non-existent fields — use `readQuery + writeQuery`.** `cache.modify` skips a field that does not yet exist, so a "build a fresh connection if `existing == null`" branch under `cache.modify` is dead code; cold-cache cases (e.g. direct landing without SSR seed) silently lose the new edge. `readQuery` returns `null` for a cold cache and `writeQuery` writes either branch unconditionally — that is the correct seam for Connection updates.
- **Connection create.** Use `readQuery + writeQuery` to append a `{ cursor, node }` edge and bump `totalCount`. On a cold cache, build a minimal `<Type>Connection` with `pageInfo.hasNextPage = false` so the IO loop stays idle. A leading `cache.writeFragment` is only required when the appended `node` is a **partial** projection: an edge whose `node` already carries the entity's full `{ __typename, id, …queried fields }` is normalised into the standalone `<Type>:<id>` entry by the `writeQuery` itself, so `writeFragment` is redundant. `useCreateCardgroup` and `useImportMaster` both append a complete `{ id, name, updatedAt }` node and therefore skip `writeFragment` — do not "fix" them to add it.
- **Connection create across features (a write in feature A seeds feature B's connection).** When a mutation in one feature produces an entity that belongs to a *different* feature's paginated list — e.g. `importMasterCardgroup` (the `/catalog` feature) creates a `Cardgroup` that must appear on `/cardgroups` — the mutation's `update` callback prepends to the *other* feature's connection. It MUST import that feature's exact default-vars object **and** document (`CARDGROUPS_DEFAULT_VARS` + `MyCardgroupsConnectionDocument` from `app/cardgroups/queries`), never a locally re-spelled `{ first: 20, search: null }`, so the cache key matches that feature's SSR seed and `useQuery`; a re-spelled key splits the cache and makes the prepend invisible on the target route. Worked example: `frontend/src/app/catalog/use-import-master.ts`.
- **Connection delete.** Filter the edge out of the cached connection, decrement `totalCount` (clamped at 0 — the deleted item may live on a page that was never fetched into edges), then `cache.evict` + `cache.gc()` to drop the normalised entity. Eviction alone is insufficient — the connection field is a list of `{ cursor, node }` objects whose `node` reference is broken by evict but the parent edge stays in the array.
- **Resolve an edge by `node.id`, never by `edge.cursor`.** The backend emits an opaque cursor — `"v1:" + base64(id)` on the admin-users connection, or the longer `"v2:" + base64(json)` envelope on every other connection — never the raw node id. Matching an entity by comparing a raw id against `edge.cursor` always misses: an edit-target lookup (`edges.find((e) => e.cursor === editId)`) renders the not-found state for *every* row, and a `cache.modify` filter (`edge.cursor !== id`) never removes the deleted edge. Use `edge.node.id` in render-path code and `readField<string>("id", edge.node)` inside `cache.modify` (where `edge.node` is a normalized `Reference`, not a plain object). The regression-test fixture MUST emit an opaque, prefixed value — never `cursor: id`, or a cursor-based match passes and masks the bug. The fixture does **not** have to reproduce the connection's actual envelope: the only property that makes the regression detectable is that the cursor is not the raw node id, so the shorter `"v1:" + btoa(id)` stand-in is the sanctioned shape on every v2 connection too. Building a faithful `"v2:" + btoa(json)` fixture would couple the frontend test to the Go `cursor.EncodeV2` body layout without testing anything more. Worked example: `frontend/src/app/admin/masters/admin-masters-client.tsx` is a master-catalog (v2) listing whose fixture deliberately uses the v1 stand-in; the comment at the fixture says so. Full rationale: [`docs/pagination/resolve-connection-edge-by-node-id.md`](../../docs/pagination/resolve-connection-edge-by-node-id.md).
- **Connection update (cache normalization).** Rely on Apollo cache normalization (entities with `id` are normalized by default). No manual `update` callback is needed; mutations that touch a normalised entity propagate to every cached query that reads it.
- **Drop `optimisticResponse` for mutations that can fail with typed GraphQL errors.** `@apollo/client` v3.x rolls back optimistic writes on **network** errors but not consistently on typed GraphQL errors (`FORBIDDEN`, `BAD_USER_INPUT`, etc.). For a mutation that can plausibly return one of those — e.g. a role assignment that fails authorization, or a self-demotion blocked by a server-side guard — the optimistic write persists and the cache lies until the next mount. Default posture: drop `optimisticResponse` and pay one round-trip of latency. Alternative when latency is measurable: manual rollback in the catch branch via `cache.evict({ id: ... })` + `cache.gc()`. Never leave a typed-error-capable mutation with `optimisticResponse` and no rollback.
- **Enforce the rule with a static-source regression test.** Slice the component source via `Component.toString()` (or read the file via `readFileSync` if the symbol is module-scoped), pin to the mutation call region (between `mutationName({` and `.catch(`), and assert `not.toContain("optimisticResponse")`. This catches accidental reintroduction at test time without runtime mocking. Worked example: the `"does not carry optimisticResponse in the handleSwipe mutation"` test in `frontend/src/app/learn/[cardgroupId]/learn-client.test.tsx`. The same pattern is documented in [`docs/frontend/typescript-conventions/static-grep-regression-guard-test.md`](../../docs/frontend/typescript-conventions/static-grep-regression-guard-test.md).
- **Pick one data-loading mode per component.** A component that accepts both an SSR-prop variant (`{ initial: T }`) and a query-id variant (`{ id: string; query }`) ends up with `useState(props.initial ?? "")` or similar — the state initializes once before the query resolves and stays at the empty default. The two modes are not interchangeable. Decide at the call site (RSC seed vs. client-driven fetch) and keep the component single-mode. If both modes are needed at different routes, write two thin wrappers around a shared presentational component instead of branching inside.

## Frontend pagination UX

- **The shared `useConnectionPagination` hook is the single IO owner; consume it, never re-inline the loop.** All five cursor-paginated list screens (cards / cardgroups / catalog / admin masters / admin users) route their pagination through `frontend/src/lib/pagination/use-connection-pagination.ts`. The hook owns the underlying Apollo `useQuery` and exposes `refetch` for screens that render a query-error-banner Retry or a mutation-conflict reload — take `refetch` from the hook return, never re-add a parallel `useQuery` for the same document (double-subscribe / cache split). The `pagination-ref-triplet-removal-rule.test.ts` guard enforces that a migrated screen carries no inline `new IntersectionObserver` / `useEffectEvent`. The four recurring migration traps (refetch sourcing, sibling-query retention, cache-key preservation, regression-guard move) are in the migration harness under Further reading.
- **A mounted-but-inactive consumer passes `skip: !open` so it issues no query until activated.** A sheet/dialog that its parent keeps *always mounted* (to drive open/close animation) but that calls `useConnectionPagination` fires the underlying `useQuery` on mount — even when the user never opens it — so every render of the parent route pays a network round-trip on a cold cache. The shared hook accepts an optional `skip?: boolean` (threaded straight into `useQuery`'s `skip`; defaults to `undefined`/false, so the five list screens that omit it are unaffected). Pass `skip: !open` from the always-mounted consumer; the query then fires only on first open and re-uses the cache on subsequent opens. This mirrors the `cardgroup-picker-sheet.tsx` `skip: !open` precedent (which gates a bare `useQuery`). Worked example: `frontend/src/components/cardgroups/merge-from-catalog-sheet.tsx` is always mounted by `CardgroupCardsSection` and passes `skip: !open`.
- **`fetchMoreError != null` halts the IO loop.** Without an error halt gate, the IO keeps firing on the same failed cursor and loops invisibly with only `console.error` noise. Set state to a banner string in the `fetchMore` `.catch`, render a Retry button that clears the state and re-invokes the request, and short-circuit the IO `useEffect` while the error is set.
- **`useEffectEvent` for observer-owned latest-value reads; normal callbacks for Retry.** In React 19.2, the observer callback should call an Effect Event that reads the latest committed `hasNextPage`, `endCursor`, and `searchQuery` values. The Effect Event must only be invoked from the Effect-owned `IntersectionObserver` callback, not from UI event handlers like Retry buttons. Retry should call the parameterized `fetchNextPage({ hasNextPage, endCursor, searchQuery })` helper directly. Keep `fetchingRef` as the explicit same-tick mutex because `useEffectEvent` does not serialize overlapping `fetchMore` calls and `useTransition` does not block synchronous repeated observer fires before pending state commits. This describes the IO-owner (the shared hook) internally; a consuming list screen calls the hook's exposed `retryFetchMore`, not its own `fetchNextPage`.
- **`NetworkStatus.fetchMore`, not magic number.** Always import the named `NetworkStatus` enum from `@apollo/client`. Magic numbers silently rot if Apollo renumbers (vanishingly rare, but the named import costs nothing).
- **`migratedSites` registers the file that carries the `useConnectionPagination` literal — never a caller one level up that lacks it.** `pagination-ref-triplet-removal-rule.test.ts`'s migrated-site rule greps each listed source for the literal string `useConnectionPagination` (Rule 3), so `migratedSites` must list whichever file actually calls the shared hook. The three per-entity cards screens (cardgroup cards, admin master cards, catalog deck cards) do NOT call `useConnectionPagination` directly: they delegate through the shared `useEntityCardsConnection` factory (`src/lib/pagination/use-entity-cards-connection.ts`), which is the single site carrying the literal and the one registered in `migratedSites`. The thin per-entity wrappers (`use-cards-connection.ts`, `use-master-cards-connection.ts`, `use-catalog-cards-connection.ts`) and their client components (`cards-client.tsx`, `master-cards-client.tsx`, `catalog-deck-client.tsx`) all lack the literal — registering any of them would fail Rule 3. A screen that builds its OWN wrapper directly over `useConnectionPagination` (rather than the cards factory) registers that wrapper. A review agent that suggests adding a wrapper or client on top of the factory is wrong — verify against the guard's actual `expect(source).toContain("useConnectionPagination")` assertion, not the suggesting prose.
- **The cards-connection wrapper hooks localize their fetchMore fallback via a `fetchMoreErrorMessage` prop, and the namespace tracks the LISTED ENTITY, not the feature directory.** The hooks are not components, so the convention is to pass the localized string in rather than call `useTranslations` inside them: the shared `useEntityCardsConnection` factory takes a `fetchMoreErrorMessage: string` input and resolves it via `getBackendErrorBanner(err) ?? fetchMoreErrorMessage`; every per-entity wrapper threads the client's localized string straight through. The client keys the message by what the list actually shows: the catalog **deck-detail** view (`/catalog/[id]`) lives under the `Catalog` feature but its list is **cards**, so it passes `tCards("fetchMoreFailed")` ("load more cards"), NOT `t("fetchMoreError")` from the `Catalog` namespace ("load more cardgroups"). Reusing the feature-directory namespace would surface "cardgroups" copy on a card list. The fallback only fires when `getBackendErrorBanner(err)` returns `undefined` (field-level errors); a transport error renders `getBackendErrorBanner`'s own mapped string ("Could not reach the server…"), so a fetchMore-error test that mocks a network error must assert that mapping, not the localized fallback.
