# Playwright E2E

The E2E suite lives in `frontend/e2e/` and covers the two highest-value flows:

- admin dictionary import (`/admin/dictionary`)
- learner swipe session (`/learn/[cardgroupId]`)

## Auth model

Production login is Google OAuth only, so the E2E suite does not drive the login UI. Tests use a local Supabase stack and a test-only helper in `frontend/e2e/_auth.ts`:

1. Create or update a Supabase Auth user with `auth.admin.createUser` / `updateUserById`.
2. Upsert the matching `public.users` row defensively.
3. Upsert the needed role and `public.user_roles` assignment through the service-role client.
4. Sign in with `@supabase/ssr`'s `createBrowserClient` (configured with the anon key) using `signInWithPassword`.
5. Let `@supabase/ssr` write the auth cookie set (`sb-<project-ref>-auth-token` plus `.0` / `.1` chunks for split JWTs) and inject that set into the Playwright context.

The service-role key is read only from `E2E_SUPABASE_SERVICE_ROLE_KEY`. It is generated by `supabase start` for local or CI runs and must never be exposed through `NEXT_PUBLIC_*` variables.

### Why the Admin API + cookie injection strategy

The E2E approach deliberately avoids adding email/password login to the production OAuth UI. Using `auth.admin.createUser` / `updateUserById` and injecting the resulting cookie set into the Playwright context means zero production code changes are required to enable E2E authentication — the test helper lives entirely in `frontend/e2e/` and is never shipped.

### Supabase cookie name derivation

`@supabase/ssr` derives the cookie name as `sb-${hostname.split(".")[0]}-auth-token`. On `localhost` this produces `sb-localhost-auth-token`; on `127.0.0.1` it produces `sb-127-auth-token`. The two names are distinct and **must not be merged** — injecting only the `localhost` variant when the app runs on `127.0.0.1` silently drops the session. The helper in `frontend/e2e/_auth.ts` sets both cookies to cover whichever hostname the test runner resolves.

### JWT cookie chunking

When the Supabase JWT is large, `@supabase/ssr` splits it across chunk cookies suffixed `.0`, `.1`, etc. Cookie injection must treat the **full set** (base name plus all numbered chunks) as an atomic unit. Injecting only the base-name cookie — or only one chunk — leaves the session incomplete and the auth check fails silently.

### Email normalisation across all call sites

GoTrue (the Supabase Auth server) stores emails in lowercase internally. Every call that touches an email in the test helper — `createUser`, `updateUserById`, and `signInWithPassword` — must apply `.toLowerCase()` before passing the value. Normalising at only one call site (e.g. only on `createUser` but not on `signInWithPassword`) causes a find/create/login mismatch and the `signIn` step returns an `Invalid login credentials` error even though the user exists.

### `auth.admin.listUsers` pagination end condition

`auth.admin.listUsers` does not expose a standard `hasMore` / `nextPage` flag in supabase-js v2. The implicit end condition is `data.users.length < perPage`: when the server returns fewer users than the requested page size, there are no further pages. Use this check rather than comparing an opaque cursor, which is an internal implementation detail.

### Seed helpers: insert, don't upsert, against tables without UNIQUE

`frontend/e2e/_auth.ts` writes seed rows through the Supabase service-role client. `seedUser`, the role upsert, and the `user_roles` upsert all rely on UNIQUE columns that exist in the schema (`users.id` PK, `roles.name`, the `(user_id, role_id)` composite). `seedCardgroup` cannot follow the same template: `cardgroups` has no UNIQUE on `(owner_id, name)` (see `docs/backend-db.md` § "Postgres upsert: prerequisite UNIQUE / EXCLUSION constraint"), so `upsert(..., { onConflict: "owner_id,name" })` aborts every spec's `beforeAll` with `42P10` "no unique or exclusion constraint matching".

Each seed call site already randomises the natural key (e.g. `runId = randomUUID().slice(0, 8)` baked into the cardgroup name and card fronts), so a plain `insert` is enough. A duplicate that surfaces in CI is then a real test bug — leaked fixture data from a previous run, or two specs colliding on a key that ought to be unique per run — not a missing upsert. Before adding `upsert(..., { onConflict: ... })` to a new helper, confirm the conflict target is backed by a UNIQUE in the migrations; if it is not, choose `insert` and trust the randomised key.

## Test design

### `test.describe.serial` for DB-dependent sequences

`fullyParallel: false` in `playwright.config.ts` prevents specs in different files from interleaving, but it is not sufficient to guarantee order within a single file when `test.only` or `--repeat-each` is active. When tests in a file share database state (e.g. a seeded card deck that successive tests consume), wrap them in `test.describe.serial` so Playwright enforces strict sequential execution regardless of flags. Without `serial`, a retry or `test.only` invocation can break the assumed order and cause a test to see a database state that a previous test was meant to set up.

### Do not assert on optimistic-update intermediate states

When the backend server response replaces an optimistic update — for example the FSRS scheduler rewrites the queue order after a swipe — intermediate states like `X completed / Y remaining` are transient and polling-speed dependent. A `toBeVisible()` assertion on that text is not a stability guarantee: Playwright's auto-wait will match the element for as long as it is visible, including a flicker that resolves within milliseconds. Assert on two separate, stable values instead: the definitive `completed` count **after** the backend confirms, and the existence of at least one remaining card — not the exact remaining count tied to a transient queue state.

### `toBeVisible()` alone does not prove true state arrival

Playwright's auto-wait retries `toBeVisible()` until the element appears in the DOM and is not hidden. An element that flickers visible for one frame during an optimistic update satisfies `toBeVisible()` even though the true state has not yet arrived from the server. Combine `toBeVisible()` with a separate assertion that is only satisfiable after the authoritative server response (e.g. checking the final count, or polling for a stable aria-label) rather than relying on visibility alone.

### Active-card transition: compare aria-labels before and after

To confirm that a swipe advanced to the next card, record the active card's `aria-label` before the swipe, swipe, then assert that the new active card has a different `aria-label` **and** that the new label was not already in the set of previously-seen cards. Do not rely on the absolute position of elements in the DOM — `SwipeCardStack` mounts background cards simultaneously, so a position-based selector may match a background card rather than the truly active one.

### Scope button locators to the active card

`SwipeCardStack` mounts background cards behind the active card, and each rendered card includes its own `Easy` / `Hard` buttons. `getByRole("button", { name: "Easy" })` therefore matches multiple elements in the accessibility tree. Scope the locator to the active card's container (e.g. `activeCard.getByRole("button", { name: "Easy" })`) to avoid `strict mode violation: locator.click() resolved to N elements` failures and to ensure the action targets the foreground card.

## Local Run

Start Supabase and backend first:

```bash
supabase start
supabase status -o env
cd backend && PING_TOKEN=local-e2e go run ./cmd/server
```

In another shell, remap the output of `supabase status -o env` to the E2E variables:

```bash
set -a
eval "$(supabase status -o env)"
set +a
export E2E_SUPABASE_URL="$API_URL"
export E2E_SUPABASE_ANON_KEY="$ANON_KEY"
export E2E_SUPABASE_SERVICE_ROLE_KEY="$SERVICE_ROLE_KEY"
export NEXT_PUBLIC_SUPABASE_URL="$E2E_SUPABASE_URL"
export NEXT_PUBLIC_SUPABASE_ANON_KEY="$E2E_SUPABASE_ANON_KEY"
export BACKEND_URL=http://localhost:1323
pnpm --filter frontend test:e2e
```

Use `pnpm --filter frontend test:e2e --headed` when debugging browser state.

First run downloads Chromium via `pnpm --filter frontend exec playwright install chromium` (~150 MB). CI does this in a dedicated step; locally Playwright runs it on demand.

## CI

`.github/workflows/e2e.yml` starts Supabase, exports the local keys into the job environment, starts the Go backend, and lets Playwright build/start the Next.js app via `frontend/playwright.config.ts`. See `docs/ci.md` § "E2E workflow" for the trigger, concurrency, and retention policy.

Failure artifacts uploaded by the job:

- `frontend/playwright-report/`
- `frontend/test-results/`
- `/tmp/flamingo-backend.log`
