# Gotchas encountered

> Part of [`frontend/CLAUDE.md`](../../frontend/CLAUDE.md). See the index for related chapters.

**`app/<route>/error.tsx` does not catch errors from `app/layout.tsx`.** Next.js error boundaries scoped to a route segment only catch errors thrown by that segment's RSCs and components. Errors thrown inside `app/layout.tsx` (e.g. the `Header`) escape to `app/global-error.tsx`, or to Next's default crash page if `global-error.tsx` is absent. Keep shared layout components defensive — render degraded states rather than throwing.

**The root layout (a server component) does not re-render on client-side (soft) navigations — route-conditional chrome must be decided in a client component reading `usePathname()`.** `app/layout.tsx` runs once per full document load; the App Router does not re-execute it on a soft navigation between routes. Any decision the layout makes from the request (e.g. "mount the nav shell on every route except the bare full-screen routes `/login`, `/onboarding`, `/terms`, `/privacy`") therefore freezes at the route that triggered the last full load. The concrete bug this caused: `/login` and the public `/terms` + `/privacy` legal pages are all full-screen routes that render their own `<main>` and must show no nav shell. Opening `/terms` from the sign-in screen and navigating back via its in-page `<Link href="/login">` left the shell — nav rail included — stranded over `/login`, because the server layout froze its shell decision at whichever route triggered the last full document load and never re-ran on the soft navigation. The fix moves the shell/bare decision into a client component (`frontend/src/components/conditional-shell.tsx`) that reads `usePathname()` and re-renders on every navigation; the layout passes identity props in and always mounts it. Three things worth knowing: (1) importing the server `AuthShell`/`AppShell` into the client `ConditionalShell` pulls those wrappers into the client bundle, but the page `children` reach them as a prop and stay server-rendered — the standard RSC "client component with server children" composition. (2) The native-Next alternative is route groups (`(app)/` with a shell layout vs a bare `(bare)/`), but that is the right call only when bare/public routes are numerous or need a genuinely different root chrome; here bare routes are few and stable while "has shell" is the dominant default, so a single client branch beats an ~80-file directory move plus permanent `(app)/` import-path noise. (3) Lock the behavior with a test that `rerender`s across a `usePathname()` change (full→bare drops the shell, bare→full mounts it) — a single-render test passes even when the decision is frozen, so only a transition test catches a regression. References: `frontend/src/components/conditional-shell.tsx`, `frontend/src/components/conditional-shell.test.tsx`.

**`useRef(false)` is the correct guard for one-shot effects in error boundaries.** When an error boundary needs to call `router.replace()` exactly once, use `const hasRedirected = useRef(false)` to gate the call inside `useEffect`. Using `useState` instead would re-trigger the effect on every re-render. `useRef` mutations do not schedule a re-render and therefore cannot form a feedback loop.

**`router.refresh()` after `router.push()` refreshes the source route, not the destination.** `router.refresh()` re-renders the RSC subtree for whatever page is current at call time. Calling it immediately after `router.push("/other")` targets the *current* page before the navigation settles — the destination route does not receive the refresh. `router.refresh()` is only useful when staying on the same route (e.g. after a mutation that does not navigate). When navigating to a different route, skip `router.refresh()` entirely — the destination page is a fresh server render, so there is nothing stale to clear. Reference: `frontend/src/app/cardgroups/new/new-cardgroup-client.tsx` calls `router.refresh()` only in the no-`returnTo` branch that navigates to `/cardgroups/{id}` (a same-domain refresh of the newly-pushed page is idempotent), and skips it in the `returnTo` branch where the destination is a fully fresh render.

**Next 16 deprecates `middleware.ts` in favour of `proxy.ts`.** The build emits a deprecation warning (not an error) when `src/middleware.ts` exists. We intentionally stay on `middleware.ts` because `@supabase/ssr` templates and ecosystem docs still reference the old name. When the ecosystem catches up and Next removes the old name, rename `src/middleware.ts` → `src/proxy.ts` (and `src/lib/supabase/middleware.ts` → `src/lib/supabase/proxy.ts` for consistency).

**Biome 2 — Tailwind 4 directive parsing**: Without `css.parser.tailwindDirectives: true` in `biome.json`, directives like `@theme`, `@custom-variant`, and `@import "tw-animate-css"` can trigger false-positive lint errors. Add the flag whenever Tailwind 4 CSS is in scope.

**Biome 2 — pure-deletion diffs can trip the collapse-short-exports rule.** Biome's formatter collapses an export block onto a single line when it has few enough members. A pure-deletion PR that removes some exports from a file without touching the formatting can push the remaining block below the collapse threshold, causing the previously-passing file to now fail `biome check`. Run `pnpm biome check --write frontend/src/` after any deletion that touches a multi-export file (UI primitive barrels are the common case — `frontend/src/components/ui/dialog.tsx`, `frontend/src/components/ui/sheet.tsx`). The fix is mechanical — let Biome rewrite the block — but the failure surfaces on CI rather than in the deletion diff, so it is easy to miss locally if `biome check` is not part of the pre-commit step.

**Biome 2 — glob pattern change from v1**: `files.ignore` is replaced by `files.includes` with `!` negation patterns. Prefer `"!.next"` over `"!.next/**"` — the latter can silently fail to exclude the directory in some Biome 2 versions.

**Next.js `Metadata` type import**: `Metadata` (and `MetadataRoute`, `Viewport`, etc.) must be imported from `"next"`, not `"react"`. `ReactNode` stays in `"react"`. The two are easy to conflate when working in the App Router.

**Next 15+/16 — `themeColor` is a `Viewport` field, not a `Metadata` field.** Putting `themeColor` inside `export const metadata: Metadata` is silently ignored since Next moved viewport-affecting fields (`themeColor`, `width`, `initialScale`, etc.) out of `Metadata`. It must live in a separate `export const viewport: Viewport = { themeColor }` in the same layout/page. `appleWebApp` stays in `metadata`. Reference: `frontend/src/app/layout.tsx`; see [`pwa.md`](pwa.md) for the PWA context.

**`@t3-oss/env-nextjs` peer on Zod**: `@t3-oss/env-nextjs@0.12.0` requires `zod@^3.24.0`. Zod 3.23.x emits a peer-dependency warning that can obscure real errors. Pin Zod to `>=3.24.0` when using this package.

**Apollo imports — use `@apollo/client-integration-nextjs` for `ApolloClient` and `InMemoryCache` in browser code.** Importing those two symbols from the base `@apollo/client` package produces a client that does not handle Next.js SSR streaming and breaks hydration.

**Apollo Client v4 error type split.** `CombinedGraphQLErrors` lives in `@apollo/client/errors`, **not** `@apollo/client`. Use `CombinedGraphQLErrors.is(error)` for type narrowing, then read `error.errors[0]?.message`. The v3 pattern `error.graphQLErrors` does not exist in v4.

**Apollo Client v4 link tests must go through `ApolloClient`, not `execute(link, op)`.** Apollo Client v4 ships with rxjs internally; the `Observable` type returned by `execute` is the rxjs `Observable`, not the legacy Apollo `Observable`. Constructing a standalone `Observable.of(result)` as a terminal mock no longer works. Instead, construct an `ApolloClient` with your link chain and the mock terminal link, then call `client.query()` or `client.mutate()`. The terminal mock link should use `new Observable(subscriber => { subscriber.next(mockResult); subscriber.complete(); })` (rxjs form).

**RSC code must use `env.BACKEND_URL`, not `/api/graphql`.** The rewrite in `next.config.ts` only applies to browser-originating requests. Server components calling `/api/graphql` would hit a Next 404.

**Vitest v3+ dropped `environmentMatchGlobs`.** Use `environment` in `vitest.config.ts` for the global default and add `// @vitest-environment <name>` at the top of individual test files that need a different environment (e.g. `jsdom`). The `environmentMatchGlobs` option is silently ignored in v3+ — tests that relied on it fall back to the global default without warning.

**Vitest loads `src/env.ts` and crashes if required env vars are unset.** `vitest.config.ts` injects placeholders via `test.env` — currently `BACKEND_URL`, `NEXT_PUBLIC_SUPABASE_URL`, and `NEXT_PUBLIC_SUPABASE_ANON_KEY`. Any new required var added to `src/env.ts` (server or client) must get a corresponding `test.env` entry, otherwise Vitest crashes at module load time before any test runs. Keep values valid for their Zod schema (e.g. `z.string().url()` requires a real URL shape).

**`server-only` has no standalone npm package** — it ships inside Next.js and the Next compiler resolves it. Vitest's node env cannot, so `vitest.config.ts` aliases `server-only` to an empty stub. Without the alias, importing `src/lib/apollo/server.ts` in any test fails to resolve.

**Client components must not import from RSC files that touch `next/headers`.** A `"use client"` component that imports a utility from a file which itself imports `next/headers` (or any other Node-only / server-only API) drags the server dependency into the client bundle and the production build fails — Turbopack errors with `You're importing a component that needs "next/headers"`. The most common form of the bug is exporting a pure helper (e.g. `sanitizeReturnTo`) alongside an RSC `page.tsx` and importing the helper from a client component; even when the helper itself does not touch `next/headers`, the file's other exports do, and the whole module is pulled into the client bundle. The fix is to extract any helper that needs to be reachable from both server and client into a server-agnostic module under `src/lib/` (e.g. `frontend/src/lib/sanitize-return-to.ts`) — its JSDoc should explicitly state that it is safe to import from both contexts. The `vitest` jsdom environment does not catch this because Vitest does not run the Turbopack bundler — only `pnpm build` surfaces it (see Dev quickstart note above). Reference: `frontend/src/lib/sanitize-return-to.ts`, imported by both `frontend/src/app/cardgroups/new/page.tsx` (RSC) and `frontend/src/app/cards/new/cards-new-client.tsx` (client).

**pnpm isolation can hide transitive deps from app code.** `@graphql-typed-document-node/core` is a transitive dep of `@graphql-codegen/client-preset`, but pnpm's strict isolation does not hoist it into `frontend/node_modules` where the generated `@/generated` re-exports need it. Promote such packages to a top-level `devDependency` when the generated-import chain depends on them.

**Stale `tsconfig.tsbuildinfo` survives `rm -rf node_modules`.** After adding/removing typed packages, `tsc --noEmit` can report impossible errors like `'data' is of type 'unknown'` from cached incremental state. Delete `frontend/tsconfig.tsbuildinfo` (and `frontend/.next/`) when type errors look incompatible with the source.

**Biome 2 — `lint` flags things `format` does not auto-fix.** The formatter accepts multi-line forms that the linter then rejects (e.g. `mockResolvedValue(new Response(...))` that lint wants on a single line). Always run `pnpm --filter frontend lint` (Biome `check`) before declaring done — `format` alone is not sufficient.

**Biome 2 — generated JSX and `expect(...)` calls require `lint:fix` after generation.** Programmatically-generated JSX (e.g. from an AI agent or codemod) often produces multi-line text nodes and multi-line call expressions that fail Biome's linter. Run `pnpm --filter frontend lint:fix` (which executes `biome check --write`) to auto-collapse these shapes. This is the recovery workflow after generation; `lint` alone will flag the violations, but only `lint:fix` resolves them.

**`gqlFetch` revalidate has three states, not two.** `revalidate?: number | false` (in `src/lib/apollo/server.ts`) deliberately preserves the difference between *omitted* (Next default heuristic), `0` (no cache), and `false` (cache forever). Collapsing to a `number` default would silently merge two of them — keep the union and only forward `next.revalidate` when the caller passes it explicitly.

**Generated `graphql()` documents flow types into `gqlFetch` call sites.** `@graphql-codegen/client-preset` emits `TypedDocumentNode<TResult, TVars>`, and `gqlFetch<TResult, TVars>(doc, { variables?: TVars })` infers both from the document. Passing wrong-shaped `variables` to e.g. `HealthQuery` becomes a compile error — do not widen the signature to `Record<string, unknown>`.

**`gqlFetch` must force-add `__typename` or SSR-seeded cache reads drop fragment fields.** `gqlFetch` prints `addTypenameToDocument(doc)`, not a bare `print(doc)`: client-preset v6 omits `__typename`, and the RSC print path bypasses Apollo's links that add it on the browser. A `__typename`-less SSR payload seeded into `InMemoryCache` via `writeQuery` cannot resolve type-conditioned fragments and silently drops every fragment field, surfacing as e.g. `/catalog` showing the card count as "NaN" with a blank name. Full rationale and the test-harness asymmetry that hid it: [`docs/frontend/apollo-wiring.md` § "RSC (`gqlFetch`)"](apollo-wiring.md#rsc-gqlfetch).

**TanStack Form `onChange` validator runs synchronously on every keystroke — no built-in debounce.** For long inputs this can cause noticeable jank in tests that type character-by-character. Use `userEvent.paste("long string")` instead of `userEvent.type(...)` in tests to avoid triggering a validator call per character. In production components, add an `asyncDebounceMs` option to the field's async validator when you need network-backed validation.

**TanStack Form field errors are Zod `ZodIssue` objects, not plain strings.** `field.state.meta.errors` is `ValidationError[]` where each entry may be a `ZodIssue`. A `<FieldError>` helper component that calls `issue.message` (or falls back to `String(error)`) keeps rendering consistent across sync and async error paths.

**`navigator.sendBeacon` cannot attach Authorization headers.** `sendBeacon` is a W3C-specified API that POSTs a payload without custom headers; there is no way to attach `Authorization` or `Content-Type: application/json`. Any GraphQL endpoint that requires an `Authorization` header (e.g. a Bearer JWT) cannot be called via `sendBeacon`. The only `beforeunload` option for such endpoints is a standard `fetch` with `keepalive: true`, but modern browsers may still cancel `fetch` requests during navigation. Treat any flush triggered from a `beforeunload` listener as best-effort, not a guarantee, and document the limitation in a code comment so a future maintainer does not attempt to replace it with `sendBeacon`. See [`docs/pagination/beforeunload-flush-gate-on-pending.md`](../pagination/beforeunload-flush-gate-on-pending.md) for the implementation pattern.

**`optimisticRollback` inside a `catch` block must be wrapped in its own `try/catch`.** When a `commitDelete` rejects, the standard recovery is to call `optimisticRollback()` to restore the prior Apollo cache snapshot, then call `onCommitFailed(err)` to surface a user-facing banner. `optimisticRollback` calls Apollo's `writeQuery`, which can throw if the cache shape is inconsistent (e.g. the connection field was evicted between the optimistic remove and the commit failure). If that throw is uncaught inside the outer `catch` block, execution halts before `onCommitFailed` is called — the user never sees the retry banner and the failure is silently dropped. Wrap the rollback in its own `try/catch`, log a structured warn on rollback failure, and call `onCommitFailed` unconditionally in a `finally` clause so the user-facing signal always fires regardless of whether rollback succeeded.

**`useState` setter is already stable; don't wrap in `useCallback`.** React guarantees `useState`'s setter has stable identity across renders. Wrapping it in `useCallback(() => setStateInput(next), [])` adds zero memo value and an extra indirection. Destructure `useState` directly under the publicly-exposed name and drop both the `useCallback` wrapper and the aliased private name. Reference: `frontend/src/hooks/use-debounced-search.ts` removed the `setStateInput` alias and wrapper (commit `593e135`).

**`useMemo([alwaysNewObject])` is a no-op trap.** `useMemo` re-computes when any value in its dep array changes identity. If a dep is a fresh object/array/Set each render (e.g. `selectedIds = new Set(prev)` on every toggle), the memo's cache never hits — every render re-runs the body, and the overhead exceeds savings. Drop `useMemo` and compute inline. Reference: `frontend/src/hooks/use-bulk-selection.ts` dropped `useMemo(() => selectedIds.size, [selectedIds])` in favour of inline `const count = selectedIds.size` (commit `ddac4de`).

**`React.RefObject<T>` should use named import, not global namespace.** Importing `RefObject` from `"react"` via `import type { RefObject } from "react"` and using `RefObject<T>` bare is consistent with how the codebase imports `ReactNode`, `ChangeEvent`, etc. The `React.RefObject<T>` global-namespace form relies on ambient lookup and reads inconsistently against named imports used elsewhere. Reference: `frontend/src/app/cardgroups/[id]/cards/cards-client.tsx` was updated to use the named import instead of the global form (commit `ddac4de`).

**Next.js CSP nonce: the forwarded request header and browser response header both use `Content-Security-Policy` but serve different roles.** Next.js 16's SSR pipeline extracts the nonce for `<script nonce="...">` tag injection by reading the internal request header named exactly `Content-Security-Policy`. The middleware forwards this same header name on the *request* (for Next's server-side rendering) and sets an identically-named `Content-Security-Policy` header on the *response* (visible to and enforced by the browser). The two share a name but serve different purposes: the request-side header is an internal forwarding mechanism; the response-side header is the enforcing browser policy. A developer who reads the `Content-Security-Policy` request header from `next/headers` in a server component will receive the CSP string and must understand that the request header is not visible to the browser. The comment in `frontend/src/lib/supabase/middleware.ts` at the `requestHeaders.set("Content-Security-Policy", ...)` call site explains this distinction. See [`docs/frontend/csp.md` § "Middleware flow"](csp.md#middleware-flow).

**`new URL(url)` throws `TypeError: Invalid URL` with no context about which variable is wrong.** In security-critical code that parses URLs from env vars (`NEXT_PUBLIC_SUPABASE_URL`, external origins), `new URL(url)` throws with only a generic message when `url` is malformed. Wrap it in a try/catch that rethrows with the config variable name and the value: `throw new Error(\`[csp] invalid supabaseUrl — not a valid URL: ${JSON.stringify(url)}\`)`. Without this, a misconfigured env var crashes every middleware invocation with a `TypeError: Invalid URL` stack trace that gives no indication of which variable is the source. Reference: `frontend/src/lib/security/csp.ts` — the `parseSupabaseUrl` helper.

**Middleware-level header builders must fail gracefully — wrap in try/catch and omit the header, never throw.** A middleware that calls a header builder (e.g. `buildHtmlCsp`) without a catch block will crash every HTTP request if the builder throws (e.g., due to a misconfigured env var). Wrap the call in try/catch, log the error via `console.error`, and fall back to omitting the header so auth, cookie rotation, and routing continue to work. The pattern in `frontend/src/lib/supabase/middleware.ts` is: try to build → on failure set `cspPolicy = null` → gate all CSP header sets on `cspPolicy != null`. The principle mirrors the layout-level degradation rule in [`.claude/rules/frontend-rsc-error-handling.md`](../../.claude/rules/frontend-rsc-error-handling.md) ("the Header must degrade on failure, never throw") applied one layer earlier at the middleware.

**Scope `role="status"` / `aria-live` to the status text, not a container that also holds controls.** A live region announces ALL descendant text when its contents change, so wrapping a result section that also contains buttons (e.g. `Back`, `Done`) in `role="status"` makes screen readers announce the button labels as part of the status update. Put `role="status"` (or `role="alert"` / `aria-live`) on the status/banner element alone and keep interactive controls outside the live region. Worked example: the batch-import step-2 result section moved `role="status"` off the wrapping `<section>` onto the banner `<div>`, leaving the `← Back to edit` and `Done` buttons outside the announced region.

**Under enforcing CSP, a try/catch that omits the header on failure means zero browser protection — not just lost observation.** When CSP runs in report-only mode, a builder failure omits the observation header: violations are not reported but traffic is unblocked. The same try/catch under an enforcing policy omits `Content-Security-Policy` entirely: the browser receives no policy and applies no restrictions. The error-handling code was designed for observability loss; reassess the acceptable-failure contract whenever the mode transitions from report-only to enforcing. Reference: `frontend/src/lib/supabase/middleware.ts` — `buildHtmlCsp` catch block.

**Apollo streaming SSR scripts are NOT covered by Next.js's automatic nonce propagation.** Next.js applies the nonce to its own bootstrap and flight-data scripts, but callbacks registered through `ServerInsertedHTMLContext` — the path Apollo uses for its streaming data transport — are rendered without a `nonce` option. Under an enforcing CSP, Apollo's inline `<script>` tags are blocked unless the nonce is threaded manually via `extraScriptProps={{ nonce }}` on `ApolloNextAppProvider` (with the nonce read from the middleware-forwarded `x-nonce` request header in `layout.tsx`). See [docs/frontend/csp.md § "Apollo streaming nonce wiring"](csp.md#apollo-streaming-nonce-wiring).

**pnpm ≥11.5 fails `install` when a dependency ships a build script not declared in `pnpm-workspace.yaml` `allowBuilds`.** `pnpm install` / `pnpm install --frozen-lockfile` exits 1 with `ERR_PNPM_IGNORED_BUILDS` when a package with a postinstall/native build script is neither allowed nor explicitly denied — even though the app itself builds fine. Adding a dependency that pulls native build-script transitives surfaces this on **CI** (a fresh install), not necessarily on a local checkout that already has `node_modules`. Worked example: `next-intl@4` pulls `@swc/core` and `@parcel/watcher` (we run neither the SWC message-extraction plugin nor the native watcher), so both are listed `false` in `pnpm-workspace.yaml` `allowBuilds`. When `pnpm add <pkg>` writes placeholder entries (`'@x': set this to true or false`) into `pnpm-workspace.yaml`, do **not** revert them — replace the placeholder with `true` (run the build) or `false` (skip it; the common case for optional native bindings). Note the `pnpm.onlyBuiltDependencies` field in `package.json` is no longer read by pnpm 11.5 — the allowlist lives in `pnpm-workspace.yaml`.

**Running frontend tooling in a fresh checkout (or git worktree) — `pnpm run <script>` re-triggers `pnpm install` before the script.** pnpm's `verify-deps-before-run` runs an install check ahead of every script, so a script invocation can fail on the `ERR_PNPM_IGNORED_BUILDS` above before the script body runs. In a checkout that starts without `node_modules` (e.g. a `.claude/worktrees/<branch>` worktree), bootstrap with `mise trust` → `pnpm install` (or `pnpm --filter frontend add …`) → `pnpm --filter frontend codegen` (the generated `@/generated` tree is gitignored and must be regenerated). If the pre-run deps check blocks a tool, invoke it directly via `frontend/node_modules/.bin/<tsc|biome|vitest|next>` to bypass the wrapper. `next build` additionally needs the `src/env.ts` vars (`BACKEND_URL`, `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`) set or env validation fails at the `/sitemap.xml` page-data step.
