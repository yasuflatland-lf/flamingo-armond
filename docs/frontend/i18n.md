# Internationalization (i18n)

> Part of [`frontend/CLAUDE.md`](../../frontend/CLAUDE.md). The UI ships in English (`en`, default) and Japanese (`ja`) via [`next-intl`](https://next-intl.dev). This doc is the canonical reference every i18n change builds on.

## Approach

- **`next-intl` in App-Router-without-i18n-routing mode.** There is no `/ja` URL prefix — routes stay flat. The active locale is a per-request value resolved server-side, not a path segment. (Next.js App Router does not support the legacy `next.config` `i18n` block; that is Pages-Router only.)
- **Cookie persistence, no middleware.** The locale is read from the `NEXT_LOCALE` cookie, falling back to `Accept-Language` negotiation, then `en`. Resolution happens inside `getRequestConfig` (`src/i18n/request.ts`) — the CSP/auth middleware (`src/lib/supabase/middleware.ts`) is **not** involved.
- **Japanese lives only in JSON catalogs.** All translated copy is in `frontend/messages/{en,ja}.json`. Source `.ts`/`.tsx` stay English (see [`.claude/rules/language-policy.md`](../../.claude/rules/language-policy.md) for the sanctioned exception).

## Module map

| File | Responsibility |
|---|---|
| `frontend/src/i18n/config.ts` | `locales` tuple, `Locale` union, `defaultLocale`, `LOCALE_COOKIE`, `ogLocale` map, `toLocale` narrowing guard. The leaf of the i18n module graph (zero imports). |
| `frontend/src/i18n/negotiate.ts` | `negotiateLocale(acceptLanguage)` (pure Accept-Language parser) and `resolveLocale(cookieValue, acceptLanguage)` (cookie → header precedence). Both pure — unit-testable without a request context. |
| `frontend/src/i18n/load-messages.ts` | `loadMessages(locale)` — dynamic-imports the catalog with a fail-safe fallback to the default catalog. |
| `frontend/src/i18n/request.ts` | The `getRequestConfig` default export — wires `resolveLocale` + `loadMessages` and returns `{ locale, messages }`. |
| `frontend/src/i18n/messages.d.ts` | Augments next-intl's `AppConfig` with `Messages` and `Locale`. |
| `frontend/messages/{en,ja}.json` | The message catalogs. Identical key sets. |
| `frontend/next.config.ts` | Wrapped in `createNextIntlPlugin()` (points next-intl at `src/i18n/request.ts`). |
| `frontend/src/app/layout.tsx` | `getLocale()` → `<html lang>`; `NextIntlClientProvider`; locale-aware `generateMetadata`. |
| `frontend/src/test/render-with-intl.tsx` | Test helper that wraps a render in `NextIntlClientProvider`. |

## Locale resolution chain

`getRequestConfig` resolves the locale for every server render in this order:

1. **`NEXT_LOCALE` cookie** — the user's explicit choice (written by the language switcher).
2. **`Accept-Language` negotiation** — first-visit auto-detect.
3. **`defaultLocale` (`en`)**.

`resolveLocale(cookieValue, acceptLanguage)` is `toLocale(cookieValue) ?? negotiateLocale(acceptLanguage)`. `toLocale` returns `null` for an absent or **unsupported** cookie value, so a stale/garbage cookie falls through to negotiation instead of poisoning downstream. The resolved `locale` is provably always a member of `locales`, so the dynamic catalog import never targets a non-existent file under normal operation.

### `Accept-Language` negotiation behavior (`negotiateLocale`)

- Parses `tag;q=` weights; an absent `q` defaults to `1`.
- **Drops tags explicitly rejected with `q=0`** (RFC 7231 §5.3.1) and malformed weights (`q=abc`/`q=` coerce to `0`).
- Sorts by `q` descending; ties are broken by **source order** (`Array.prototype.sort` is stable in the pinned Node).
- Matches the **primary subtag** (`ja-JP` → `ja`). Returns `defaultLocale` when nothing matches.

## Provider + metadata wiring

The root layout (`src/app/layout.tsx`) reads `const locale = await getLocale()` and sets `<html lang={locale}>`. The layout has a single render path (the bare-vs-shell decision now lives in the client `ConditionalShell` wrapper, which renders inside `<html><body>`), so there is one `<html lang>` for every route. It wraps the tree in `<NextIntlClientProvider>` **with no props** — in a server component the provider inherits `locale`, `messages`, `now`, and `timeZone` from `getRequestConfig`, so there is no missing-key or empty-provider risk.

Locale-dependent metadata uses `generateMetadata` (not a static `metadata` export), because it must `await getLocale()`/`getTranslations()`. `openGraph.locale` is indexed from the typed `ogLocale: Record<Locale, string>` map in `config.ts` — adding a locale to `locales` forces an `ogLocale` entry (no silent `en_US` default).

## `AppConfig` augmentation — declare BOTH `Messages` and `Locale`

`messages.d.ts` must declare both members:

```ts
import type en from "../../messages/en.json";
import type { Locale } from "./config";

declare module "next-intl" {
  interface AppConfig {
    Messages: typeof en;
    Locale: Locale;
  }
}
```

- `Messages: typeof en` keys `t()` to the en catalog, so an unknown key (`t("Nav.bogus")`) is a **compile error**.
- `Locale: Locale` narrows next-intl's `Locale` from the default `string` to the `"en" | "ja"` union. Omit it and `getLocale()`/`useLocale()`/`NextIntlClientProvider`'s `locale` all widen to `string`, which silently defeats exhaustiveness (e.g. `ogLocale[locale]` would accept any string key).

## Fail-safe catalog loading

`loadMessages(locale)` wraps the dynamic `import(\`../../messages/${locale}.json\`)` in a `try/catch`. On failure it logs `console.error("[i18n] missing message catalog …")` and returns the **default-locale** catalog (always present). This converts the most likely future mistake — adding a locale to `locales` without committing its `messages/<locale>.json` — from a site-wide 500 (the dynamic import rejects at the root of every render) into a logged English fallback.

## Test harness — `renderWithIntl`

Any component that calls a next-intl hook (`useTranslations`, `useLocale`, `useFormatter`) must render inside a `NextIntlClientProvider`. Use `renderWithIntl` from `@/test/render-with-intl`:

```tsx
import { renderWithIntl } from "@/test/render-with-intl";

renderWithIntl(<MyComponent />);              // en catalog (default)
renderWithIntl(<MyComponent />, { locale: "ja", messages: jaMessages });
```

It defaults to the **en** catalog, so `t("Common.save")` resolves to `"Save"` and existing English string assertions stay valid — replace a bare `render(<X/>)` with `renderWithIntl(<X/>)` and the assertions need no change. Tests live in two trees (`frontend/src/**` co-located and `frontend/__tests__/**` broad — see [`testing-convention-narrow-vs-broad-page-tests.md`](testing-convention-narrow-vs-broad-page-tests.md)); a page-behavior change must wrap renders in **both**.

**RSC layout tests** mock `next-intl` (passthrough `NextIntlClientProvider`) and `next-intl/server` (`getLocale`/`getTranslations` stubs). Because `metadata` is now async (`generateMetadata`), resolve it once in `beforeAll`. Override `vi.mocked(getLocale).mockResolvedValueOnce("ja")` to assert the `ja` wiring (`<html lang="ja">`, `og:locale = ja_JP`). Reference: `frontend/src/app/layout.test.tsx`.

## Conventions for screen translation (downstream work)

Per-screen string extraction replaces hard-coded JSX/`aria-label`/`placeholder`/banner literals with `t("<Namespace>.<key>")`, adding the key to **both** `en.json` (verbatim English) and `ja.json` (translation). Keep the two key sets identical.

- **Client components**: `const t = useTranslations("<Namespace>")`.
- **Async server components**: `const t = await getTranslations("<Namespace>")`.
- **Interpolation**: ICU placeholders — `t("updatedAt", { date })` with message `"Updated {date}"` — so word order can differ per locale (Japanese places the date before the verb, so keep it in a `{date}` placeholder rather than concatenating `"Updated " + date`). Use ICU `plural` for counts.

Namespace taxonomy mirrors feature areas, not files: `Common`, `Nav`, `Language`, `Meta`, `NotFound`, `GlobalError`, `Settings` (seeded), plus `Login`, `Onboarding`, `Profile`, `Learn`, `Cardgroups`, `Cards`, `BatchImport`, `Errors`, `Pwa`, `Admin` for the per-area work.

### Terminology consistency

The canonical Japanese translations live in `frontend/messages/ja.json` (this doc stays English per [`.claude/rules/language-policy.md`](../../.claude/rules/language-policy.md), so it does not duplicate the `ja` strings). When translating a new screen, reuse the existing rendering of shared terms already in the catalog — cardgroup, card, profile, display name, email, bio, sign in, logout, save, cancel, the Again/Hard/Easy ratings — rather than introducing a synonym. Cross-screen consistency matters more than per-screen nuance: add a shared term to the catalog once and reference it everywhere.

## Scope boundary — backend-originated messages stay English

Field-level validation messages from the Go backend (`InputValidationError.message`) and the Apollo banner text in `src/lib/apollo/errors.ts` are surfaced in whatever language the backend returns (English today). Localizing the backend (an `Accept-Language`-aware Go layer) is a separate effort and is **out of scope** for the frontend i18n work. Frontend-authored copy is translated; backend-authored copy is not.

## `global-error.tsx` renders outside the provider

`app/global-error.tsx` replaces the root layout on unrecoverable errors, so it has **no** `NextIntlClientProvider` and must not call `useTranslations` (it would throw). Keep its copy English; read the `NEXT_LOCALE` cookie client-side only to set `<html lang>`. This mirrors the layout-throw constraint in [`.claude/rules/frontend-rsc-error-handling.md`](../../.claude/rules/frontend-rsc-error-handling.md).

## Catalog parity check

`frontend/scripts/i18n-parity.mjs` asserts that `en.json` and `ja.json` carry exactly the same flattened key set. Run it locally whenever you add or remove keys:

```bash
pnpm --filter frontend i18n:parity
```

Exit 0 = keys match. Exit 1 = prints which keys are missing from which catalog, keyed by dotted namespace path (e.g. `Cardgroups.filterPlaceholder`). Fix by adding the missing key to the deficient catalog before merging.

The script is intentionally dependency-free (Node built-ins only) and runs in under one second on the full catalog.

## Language round-trip e2e

`frontend/e2e/i18n-language-switch.spec.ts` covers the full locale-switch flow end-to-end:

1. Sign in as a seeded user.
2. Navigate to `/profile`.
3. Select Japanese via the language switcher.
4. Assert `<html lang="ja">` and that the Cardgroups nav link renders as `カードグループ`.
5. Switch back to English and assert `<html lang="en">` and `Cardgroups`.

Run with: `pnpm --filter frontend e2e -- --grep "language round-trip"`.

## Skeleton aria-labels (known constraint)

Skeleton components used as Suspense fallbacks (`LearnSkeleton`, `CardgroupsSkeleton`, `AdminUsersSkeleton`, `AdminRolesSkeleton`, `CardsNewSkeleton`, `CatalogSkeleton`) retain English `aria-label` values. The reason: a Suspense `fallback` must render synchronously, so the skeleton cannot call `await getTranslations()` — that would turn the fallback into an async component and break the Suspense contract. These labels are low-visibility (screen-reader-only loading states) and acceptable as English.
