# UNAUTHENTICATED vs FORBIDDEN: message asymmetry

When mapping `extensions.code` to a user-facing banner, treat `UNAUTHENTICATED` and `FORBIDDEN` differently. Collapsing them to a single generic auth message loses information the user can act on.

## The rule

- **`UNAUTHENTICATED`** → generic copy ("Your session has expired. Please sign in again.") **and** redirect the user toward `/login`. The only recovery is to re-authenticate, so the server's specific reason adds nothing.
- **`FORBIDDEN`** → preserve the server's banner message (via `getBackendErrorBanner(err)` or `toMessage(err)`). The server message names the *specific* reason ("cannot delete a protected role", "you cannot demote your own admin role") that the user needs to understand why the action was refused.

## Why the asymmetry

`UNAUTHENTICATED` and `FORBIDDEN` look similar at the transport layer (both come back as GraphQL errors with `extensions.code`), and a naïve handler treats them identically:

```ts
// Anti-pattern — loses FORBIDDEN's specific reason.
if (codes.includes("UNAUTHENTICATED") || codes.includes("FORBIDDEN")) {
  setError("Your session expired or you lost permission. Please sign in again.");
  return;
}
setError(toMessage(err));
```

The bug surfaces in real flows like the admin role delete. The UI disables delete for system roles, but a race (a concurrent role promotion) can still cause the server to return `FORBIDDEN` with message `cannot delete a protected role`. The generic auth copy hides that message — the user thinks they need to sign in again, signs out, signs back in, retries, and gets the same failure. The actionable message ("this role is protected, you can't delete it") never reaches them.

The asymmetric handling is:

```ts
const codes = liftGraphQLCodes(err);

// UNAUTHENTICATED collapses to a generic sign-in prompt — the user has
// no actionable detail to recover from.
if (codes.includes("UNAUTHENTICATED")) {
  setError("Your session has expired. Please sign in again.");
  console.warn("[admin/roles] deleteRole auth failure", { roleId: id, codes });
  return;
}

// All other codes (including FORBIDDEN): keep the server's specific reason.
console.warn("[admin/roles] deleteRole rejected", {
  roleId: id,
  name: err instanceof Error ? err.name : "unknown",
  codes,
});
setError(toMessage(err));
```

## Worked example

`frontend/src/app/admin/roles/admin-roles-client.tsx`, `handleDelete` → `scheduleDelete({ onCommitFailed })` — the branch above is the production pattern. The corresponding test (`frontend/__tests__/admin-roles-crud.test.tsx` → `shows an error banner when deleteRole returns FORBIDDEN`) pins the server message reaching the banner: the assertion is `toHaveTextContent(/cannot delete a protected role/i)`, not the generic copy.

## When the asymmetry does not apply

For non-delete-style flows where the FORBIDDEN message is generated by the gateway rather than the resource owner — e.g. an admin gate that returns a bare `permission denied` for every forbidden mutation — the server message is no more informative than a generic copy. In those cases either branch is fine. The asymmetry pays off whenever the resource owner has a specific reason to give (system role, ownership rule, self-demotion guard).

`UNAUTHENTICATED` is unambiguous: there is no scenario where the server's specific message is more useful than "sign in again". Always collapse it.
