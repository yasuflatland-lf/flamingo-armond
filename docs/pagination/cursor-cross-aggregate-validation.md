# Cursor cross-aggregate validation → `BAD_USER_INPUT`

> Part of the [pagination](../../.claude/rules/pagination.md) rules. Cross-referenced by `docs/backend.md` and `frontend/CLAUDE.md`.

A cursor pointing at a master card in another deck (the connection orders by `position`) is treated as a malformed user-supplied parameter. Returning `UNAUTHENTICATED` would leak existence of master cards in other decks; `BAD_USER_INPUT` with `field = "after"` is the correct posture. `TestMasterCard_ListMasterCards_CursorCrossGroupRejected` covers this on `adminMasterCardsConnection`. Cards by cardgroup use fixed `id ASC` ordering with no hydration and skip the cursor scope check; the page query remains scoped to the authorized cardgroup.

Owner-scoped Connection queries without a parent aggregate, such as `myCardgroupsConnection`, also reject foreign cursors as `BAD_USER_INPUT` with `field = "after"`. Cardgroups are ordered by `updated_at` alone, so `resolveCardgroupCursor` in `backend/internal/usecase/cardgroup.go` hydrates every cursor through `FindByID` plus the ownership comparison, giving unknown and foreign cursors the same rejection behavior. The [scoped `id`-order shortcut](../../.claude/rules/pagination.md#server-side-design) used by the card connection is also safe, because its result depends only on the cursor string within an already scoped query, not on whether the cursor row exists.
